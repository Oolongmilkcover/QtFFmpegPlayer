## 1. 多线程死锁：同一线程二次加锁 + 锁顺序相反

**现象**：做逐帧回退时程序直接卡死，界面无响应，日志停在固定位置不再刷新。

**排查**：一开始怀疑是回退逻辑的判断写错了（毕竟那段下标运算很绕），加日志打了半天发现卡在
`FrameQueue` 的取帧函数里面；用调试器看线程栈，才确认是锁的问题而不是逻辑问题。

**根因**：两个毛病叠在一起：
1. `getNextFrame()` 在**持有"回放队列锁"**的分支里递归调用自己，而 `std::mutex` 不可重入 —— 等于自己把自己锁死；
2. `moveToPBQ()` 持有回放队列锁再去拿帧队列锁，别的路径顺序正好相反（AB-BA）；
   更糟的是它在持锁时还读了另一个队列的 `serial` 字段，而那个字段没被同一把锁保护。

**解决**：我没有去"统一加锁顺序"，而是把未来队列和历史队列**合并成一把锁**——它俩本来就是同一组不变式
（消费未来帧的同时要写进历史），一把锁反而更简单；递归改成循环；跨线程取帧改成返回**堆上的副本**
（`av_frame_clone` + `delete`），不再把内部数组指针交给别的线程。

后来我把这条记成了：**同一个不变式就用一把锁**，而"不可重入锁 + 递归调用"是最容易自己锁死自己的组合。

## 2. Seek 时 UI 卡死

**现象**：拖进度条时整个界面冻结，一直到 seek 完成才恢复。

**解决**：
- seek 只做"登记请求"：记下目标毫秒、serial 加一、置 `m_isSeeking`、禁用按钮，然后**立刻返回**；
  真正的清队列 / flush / `av_seek_frame` / 定位全部放到 demux 线程的主循环里做，完成后发信号恢复按钮；
- demux 主循环里我把处理顺序写死：**逐帧回填 → seek → 暂停 → 时钟 → 读包**，保证控制类的请求优先被处理。

这件事后来还有后续：只把 seek 挪进 demux 线程是不够的。如果 demux 线程正好**阻塞在包队列 `push()`** 上
（队列满），seek 请求照样进不来。所以我后面又把投递改成**带超时的非阻塞投递 + 失败暂存重试**，
才算真正做到"控制线程随时能响应"（见第 8 条）。

## 3. 暂停后音频仍在播放

**现象**：点暂停，画面停住了，但声音还在响或者有余音。

**根因**：音频是独立线程，而且声卡里已经排了缓冲数据。只置一个 `bool` 标志既不会让声卡停下，
也不会把已经写进声卡的数据丢掉。

**解决**：
- **暂停**用 `QAudioSink::suspend()`，恢复用 `resume()`（`AudioPlayer` 里用一把 mutex + 状态位保证幂等）；
- **seek 之后**才用 `QIODevice::reset()` 把声卡缓冲里的残留丢掉，同时复位 `swr` 和 `atempo` 滤镜；
- 解码线程和播放线程各自有暂停标志，避免"解码还在跑、缓冲又被塞满"。

我一开始把 `reset()` 当成暂停手段用了，其实它只负责"丢残留数据"，暂停得靠 `suspend()`。

## 4. Seek 过程中点击按钮崩溃

**现象**：seek 还没结束的时候点按钮，偶发崩溃。

**根因**：seek 期间队列被清空、serial 变了、有些指针处于中间态，这时候 UI 操作会读到不一致的状态。

**解决**：
- seek 开始时 `disableBtn()`、结束时 `ableBtn()`（走信号槽，别直接在别的线程碰 UI）；
- 后来我把"**禁止操作**"改成了"**先收尾再执行**"：比如逐帧模式下拖进度条，会先退出逐帧（并把播放位置对齐）
  再执行 seek，而不是直接 `return` 把用户的操作吃掉。

## 5. 播放节奏异常：不要用 1000/fps 当每帧时长（v1.0 就有的坑）

**现象**：纯视频流（没有音频轨）的文件播放速度明显不对，我印象里是偏慢、像 0.5 倍速；
但只要有音频轨就完全看不出来。

**排查**（这个坑我从 v1.0 找到 v2.0，走过不少弯路）：
1. 先怀疑异步投递有问题：帧投给 GUI 线程之后没刷出来 —— 排除了，画面是在刷新的，只是节奏不对；
2. 又怀疑 `msleep` 精度太差，睡不够或者睡过头 —— 顺手把睡眠改成了按**绝对时间对齐**的
   `sleepUntil()`（这个改动本身有价值，但没解决这个问题）；
3. 还怀疑过"一个包里解出多帧"，导致我按帧计数算错了时长；
4. 最后才回到最基础的地方：**我用 `1000/fps` 算每帧该显示多久**（那个文件我按 60fps 折算成 16ms 一帧），而这个 fps 根本代表不了
   "这一帧实际该显示多久"。

**根因**：两层错误叠在一起。

1. **时间轴不该用帧率去推**。`AVStream::avg_frame_rate` 只是容器声明的平均值，VFR（可变帧率）视频里没有意义；
   `r_frame_rate` 对隔行视频常常是**场率**（约等于 2 倍真实帧率）。真正权威的只有这一帧和上一帧的 **pts 差**。
2. **我把"一个 AVFrame"当成了"屏幕上一帧画面"**。`AVFrame` 其实是解码器的**一次输出**：隔行视频里
   一幅画面由上下两个场（两次输出）组成；反过来一次输出也未必是新画面。而解码器还有重排序，
   一次 `send` 之后可能 recv 到 0 帧，也可能分几次 recv 才取完。

**为什么带音频时看不出来**：有音频轨时是**音频 pts 推着视频走**（音频做主时钟），每帧什么时候该显示由音频时钟
说了算，我用错的那个"帧时长"只落在兜底分支上，所以看不出问题。一旦是纯视频流、视频自己做主时钟，
这个错误就被直接放大成"播放速度不对"。

**解决**：
- 视频做主时钟（无音频 / 尾帧阶段）时，帧间隔一律取**相邻帧 pts 差**（`interval = pts[n] - pts[n-1]`），再按倍速换算；
- 音频做主时钟时，`1000/fps` 只当"目标间隔 + 异常兜底"（间隔 ≤ 0 或者大得离谱时回退到帧时长）；
- fps 只在拿不到有效 pts 的时候才用。

后来我把这条记成了：**媒体时间轴只有 pts / duration 是权威的**，"帧号 × 帧时长"这种算法在真实文件上迟早翻车。

## 6. Seek 等待时间异常 / 定位不精确

**现象**：跳转距离越大等得越久；而且 seek 之后起点会有偏移。

**根因**：
1. `av_seek_frame()` 要的是**流 time_base** 单位的时间戳，而且必须和包的 pts 在同一坐标原点；
   UI 层的毫秒必须用 `av_rescale_q()` 转过去；
2. seek 只能落在**关键帧**上，所以必须从关键帧一路解码到目标位置 —— 跳得越远，要解码的帧就越多。

**解决**：统一时间基换算；用 `AVSEEK_FLAG_BACKWARD` 定位到目标之前的关键帧，再解码到目标帧。

这里我一开始为了"快"，在定位阶段设了 `skip_frame = AVDISCARD_NONREF`（只解参考帧）。
它确实更快，但结果会停在**目标时间之后的第一帧 I/P 帧**上，位置偏几帧 —— 播放时看不出来，
做逐帧的时候就非常明显了。现在改成完整解码定位，而且渲染线程记录的是"**实际显示那一帧**"的 pts，
不再是"我请求的那个时间"。

## 7. 播放末尾画面异常

**现象**：播到结尾时画面跳变、尾帧丢了，或者干脆立刻从头重播。

**根因**：demux 读完所有包之后马上执行 `seek(0.0)` 或者切下一集，但这个时候解码器内部缓冲
和未来帧队列里还压着若干没显示的帧，被直接丢掉了。

**解决**：加了一个尾帧阶段和一个播完标志：
- demux 读到 EOF → 置 `lastSome`，让渲染线程**暂停按 diff 丢帧**，按顺序把剩下的帧播完；
- 渲染线程播完置 `playDone`；demux 看到 `playDone` 才去 `seek(0.0)` 或者切下一集。

这两个标志是**跨线程的原子量**（`std::atomic<bool>`），不是 Qt 信号槽 —— 这里用信号槽会引入线程亲和和排队延迟的问题。

## 8. CPU 饥饿导致整条流水线停摆

**现象**：seek 之后音视频只播了不到 1 秒就整体不动了。不崩溃、不死锁，判断条件也全都对。

**排查过程**：
1. 先怀疑 seek 之后死锁：逐段加日志，发现 demux 线程并没有卡在锁上，而是**在正常循环**；
2. 再怀疑时间轴错乱（音频时钟没锚定）导致视频一直丢帧：打印 `diff = videoPts - audioPts`，
   确实持续为负、视频在丢帧，但这解释不了"音频为什么也停了"；
3. 用调试器看：**所有线程都是就绪状态**，没有线程阻塞在 wait 上，可画面和声音都不动；
4. 最后从日志里看出来：demux 的判断条件全都正确，却一直没机会推进 —— 包队列和帧队列都被耗尽了。

**根因**（调度层面）：
- 正常播放时，demux 主循环有两个**天然阻塞点**：队列满时 `push()` 会等、`av_read_frame()` 有 I/O，
  线程频繁让出时间片；
- **seek 之后这两个阻塞点同时消失**：`clear()` 把队列清空了（不会满），本地文件的读指针又落在系统缓存里
  （I/O 几乎瞬时返回）。于是 demux 进入一个极紧凑的忙等循环，独占一个核心几乎不让出 CPU；
- 饥饿就这样传导下去：音频播放线程抢不到 CPU → 声卡缓冲消费不掉 → 音频数据断供、音频时钟冻结
  → 渲染线程看到 `diff` 一直为负 → 一直丢帧 → 画面卡死。

**解决**：当时是在 `run()` 循环末尾加了一行 `msleep(1)`，问题就消失了 —— 相当于给生产者补了一个显式的限速节拍。

后来我又把这块改彻底了：让生产者**阻塞在一个带超时的等待上**。包队列改成
`push(pkt, serial, timeoutMs)` / `tryPush(...)`，超时就返回 false、把包暂存到 `m_pendingPkt`，下一轮先重试它。
这样每一轮要么睡在 `wait_for()` 上（天然限速），要么超时返回去处理 seek / 回填 / 退出（不牺牲响应性），
就不用再纠结"去掉 msleep 会忙等、留着 msleep 同步收敛慢"了。

我把这条记成了：生产者-消费者模型必须给生产者限速，而"队列满才阻塞"这种限速**一旦队列被清空就失效**
（seek 就是典型场景），必须另补一个显式手段。

## 9. diff 超过阈值时的无限阻塞（背压环）

**现象**：做倍速功能的时候，seek 之后或者调完倍速之后**偶发永久卡死**，画面不动。

**排查**：一开始以为是上一条的 CPU 饥饿，加 `msleep` 没用。在不同位置打日志之后才看清：
demux 线程阻塞在**视频包队列的 push** 上，音频包因此断供，最后整条链路停摆。

**完整因果链**：

```text
seek / 倍速切换造成时间轴小跳变
  → diff = videoPts - audioPts 超过阈值
  → 渲染线程进入"只睡（等音频）却不消费帧"的分支
  → 视频未来帧队列（16 帧）被解码线程填满
  → 视频解码线程阻塞在 getWritable()
  → 视频包队列被塞满
  → demux 线程阻塞在 push(视频包)
  → 音频包也不再被投递
  → 音频帧队列耗尽，音频播放线程卡在 getReadable()
  → 音频时钟 m_audioPts 冻结
  → 渲染线程每次醒来发现 diff 还是超阈值 → 继续睡
  → 永久卡死
```

**解决**：加了个"看门狗"——如果本轮音频时钟和上一轮**一模一样**（说明时钟被冻住了），就强行消费一帧把环断开：

```cpp
if (diff > SYNC_THRESHOLD) {
    if (audioPts == m_lastAudioPts) {
        m_frameQueue->next();      // 宁可跳一帧，也要把背压环断开
    } else {
        m_lastAudioPts = audioPts;
    }
    sleepUntil(now + m_frameDurationMs);
    continue;
}
```

我一开始把这条也归到"CPU 饥饿"里去了，后来发现不是：**第 8 条是抢不到 CPU，这一条是依赖成环**。
判据是——出问题时**音频包队列是空的、视频包队列是满的、音频时钟冻住了**：这是逻辑上的环依赖，
即使 CPU 完全空闲，这个环也不会自己解开。

想彻底解决的话，方向是让"时钟源的供给"不被视频背压堵死，比如读包层按"**总队列上限 + 音频优先**"来判断
要不要等（而不是随便哪个流队列满了就整体阻塞），或者视频落后时**主动丢帧**而不是"只睡"。

## 10. 环形队列不能当"历史窗口"用（v1.0 的 rindex_shown 只能退一帧）

**背景**：v1.0 的时候我照 ffplay 的 `frame_queue` 做了 `keep_last` / `rindex_shown`：消费一帧时
先不推进 `rindex`，把刚显示过的那一帧留在队列里，所以能"退回一帧"、也能重绘。这个机制本身很好用，
但它天生只能回退**一帧**（再往前就被新帧覆盖了）。

为了做"伪无限上一帧"，我才动手重构帧队列：预分配环形数组留给未来帧，
历史帧另起一个**能往更早方向插帧**的结构。

**问题**（当时想复用同一个环形数组，再用几个布尔量切换"当前是在历史里走还是在取新帧"）：
1. 环形队列的不变式是"**一段连续的已填充区间**"（`size = (windex - rindex + N) % N`），
   只支持尾部进、头部出；而"回退"要求**往更早的方向前插**（新数据比手里所有数据都旧），
   环形数组根本没有这个原语：要么让读指针反向越过存活数据（把最新的帧覆盖掉），要么整体搬移（退化成 O(N)）；
2. 用 `switchNextMode / PrevToNext / NextToPrev` 这几个布尔量表达"当前模式"，状态会组合爆炸，
   补丁越打越多，最后自己都推不清；
3. 还有一点我当时想错了：以为环形复用能省内存。其实环形队列复用的是**容器（`AVFrame` 结构体）**，
   不是像素 —— 只要我还持有那一帧的引用（refcount > 0），解码器就不能复用它的 buffer，
   历史帧天然占内存（1080p 一帧 ≈ 3.11MB）。

**解决**：
- 未来队列继续用**预分配环形数组**（这块本来就没问题，ffplay 也是这么干的）；
- 历史改成 `std::deque` + 一个"光标"下标：前插是 O(1)，光标就代表屏幕当前那一帧，
  容量和淘汰策略都显式写出来。

后来我把这条记成了：数据结构要匹配访问模式（单向流动 → 环形；双端窗口 → deque；随机定位 → 索引 + 缓存），
以及"缓存历史本质是**用内存买后退距离**"，必须自己定好预算。

## 11. 帧级精确回退：坐标系统一 + 淘汰策略的前进性

**现象**：逐帧回退能正常触发 seek，但**位置完全不对**（跳到不相干的地方），进度条也跟着乱跳。

**根因一（坐标系）**：我的代码里约定 `AVFrame::pts` 存**毫秒**（解码线程会做一次 `av_rescale_q` 换算），
但往队列里填帧其实有**两条**路径（正常解码 / 回填解码），我**只在正常解码那条路上做了换算**。
于是历史里混进了 90kHz 时基的**原始时间戳**：
- 退回这些帧的时候 `pts` 是原始值，进度条显示就乱了；
- 更致命的是**下一次回填的"边界 pts"也成了原始值**，反算出来的 seek 目标完全是错的；
- 退出逐帧时的位置对齐（`pos = 显示帧pts / totalMs`）也被污染了。

**根因二（淘汰策略）**：历史容量有限，而回填是往更早方向插帧。如果容量满的时候优先丢掉"刚回填进来的帧"，
回填就**永远没有进展** → 反复 seek、空转。

**解决**：
- 抽出**唯一的换算点** `framePtsMs(frame, timeBase)`，所有填帧路径都必须经过它；
- 逐帧对齐改成**按毫秒 seek**（`seekToMs()` / `requestSeekMs(ms)`），不再走
  `pos = pts/totalMs` 再 `*totalMs` 那种浮点往返 —— 那个往返可能多出 1ms，`frameMs >= seekMs`
  就会落到**下一帧**；
- 回填只收集**严格早于边界**的帧（边界帧已经在历史里了，不重复入队）；
- 淘汰策略改成丢"**离光标最远的最新帧**"，保证每次回填都确实往前走了一步。

我把这条记成了：**同一个物理量（时间 / 坐标 / 单位）只能有一个换算点**；缓存淘汰策略必须保证前进性。

---

## 12. 回填期间必须独占解码器

**现象**：偶发错帧，画面错位 / 花屏一闪而过。

**根因**：解码线程在做一个包的 `send` + 若干次 `recv` 的过程中，seek / 回填线程会插进来也调用
`send/recv`。`AVCodecContext` 不是线程安全的，而且**"给每个函数都加锁"并不够**——
锁的粒度必须覆盖"一次逻辑操作"（一个包的完整解码），否则两条线程的输出会串。

**解决**：
- 加了个**解码闸门** `m_decodeGate` + `m_stepDecoding` 标志：解码线程**pop 到包之后**才拿闸门，
  并且一个包的 `send + recv` 在闸门内连续做完；
- 回填时先置 `m_stepDecoding`，让解码线程退出当前的 `recv` 循环，再独占闸门；
- 回填结束后再清一次未来帧队列，把这段窗口里解码线程可能写进去的陈旧帧丢掉。

有个细节：`pop()` 必须在闸门**外面**，否则解码线程会"拿着闸门阻塞在空队列上"，把回填直接锁死。

## 13. 所有权契约：谁申请谁释放

**现象**：偶发内存泄漏，还有潜在的重复释放风险。

**根因**：
- `push(pkt)` 在 abort 分支内部会 `av_packet_free()`，其它失败分支却不释放；`send(pkt)` 的几个提前返回
  分支也不释放 —— 调用方**根本没法知道这次调用到底有没有接管所有权**；
- 早期我还把 `new Frame(...)` 用 `free()` 释放（而不是 `delete`），这既是 UB，也不会执行 `~Frame`，
  里面的 `AVFrame` 就漏了。

**解决**：定死契约并写进接口注释：
- **入队成功 = 队列接管所有权；返回 false = 不接管，调用者负责释放**；
- `new` 出来的对象一律 `delete`（`~Frame` 里做 `av_frame_free`）；
- 跨线程传帧用 `av_frame_clone`（只加引用计数，不拷像素），谁 clone 谁负责释放。

## 14. 渲染端背压：不要让"上屏"无限堆积

**现象**：拖动或移动文件对话框时，`paintGL` 里打印的屏幕渲染 FPS 会掉；GUI 线程被长时间占用时
内存还会涨，松手之后画面会"快进"把积压的帧补播一遍。

**根因**：上屏这条路上，渲染线程是**每帧投递一个 `Qt::QueuedConnection` 调用**给 GUI 线程，**没有在飞上限**。
GUI 线程一忙（模态对话框、拖窗口、重绘），事件队列里就攒下一堆**带着整帧 buffer** 的投递
（1080p 一帧 3MB），既吃内存，又要在空闲之后逐个补播。

**解决**：
- 在 `VideoWidget` 里加了"**在飞帧数 = 1**"的丢帧邮箱（`beginPaint()/endPaint()`）：GUI 线程还没消化完上一帧，
  渲染线程就**直接丢掉这一帧**，而不是继续排队；
- 投递目标用 `QPointer` 保护，免得 widget 先析构了还在投；
- 当时判断"到底是哪边的问题"用的就是 `paintGL` 里每秒打印的那个 FPS：**它变小但没停**说明 GUI 线程没被阻塞，
  只是每帧的工作量和窗口合成开销在打架；**它彻底不打印了**才说明事件循环被外部模态消息泵占住了。

## 15. 每帧 3MB 的中间拷贝完全可以省掉（零拷贝上传）

**现象**：1080p 播放时 CPU 偏高，拖动窗口时掉帧更明显。

**根因**：`VideoWidget::setPaint()` 先把 YUV 三个平面 `memcpy` 到我自己的 `datas[]` 缓冲，
`paintGL()` 再把这份缓冲传给纹理 —— 同一帧数据被搬了两遍（一次 CPU 拷贝 + 一次纹理上传），
还白白多占了 3MB 常驻内存。GUI 线程一忙，这些拷贝还会在事件队列里排队。

**解决**：`setPaint()` 只**接管 `AVFrame` 的引用**（不拷贝），`paintGL()` 直接从
`frame->data[plane]` + `linesize` 上传：
- 行宽正好等于平面宽度时，一次 `glTexSubImage2D` 就够；
- 有行对齐 padding 时逐行上传，但源依然是解码器的内存，没有中间拷贝；
- 上一帧的引用等下一帧到了才还，保证 `paintGL` 期间数据一定有效。

## 16. 从工作线程 emit 信号直连到 UI

**现象/隐患**：偶发 UI 异常，尤其 seek 那段时间。

**根因**：`DemuxThread` 的方法既可能被 GUI 线程调用（用户操作触发 seek），也可能在 **demux 线程内部**
被调用（seek 完成后 `emit ableBtn()`）。Qt 的 `AutoConnection` 在"发射线程和接收者的线程亲和相同"时走**直连**，
于是 UI 代码（比如 `ui->ctrlbar->setDisabled()`）就在 **demux 线程**里被执行了 ——
而 Qt 要求 widget 只能在 GUI 线程访问。

**打算怎么改**：把这类跨线程通知都改成显式队列投递（`QMetaObject::invokeMethod(this, ..., Qt::QueuedConnection)`，
或者连接的时候直接指定 `Qt::QueuedConnection`），或者干脆改成"原子状态标志 + GUI 定时器轮询"。

这里我踩的认知点是：Qt 里"同一个线程亲和"不等于"同一个线程执行"，判断直连还是队列连接，
要看**发射的那一刻在哪个线程**。

## 17. 网络流导致退出卡死（av_read_frame 阻塞）

**现象**：播放 RTSP 这类网络流的时候，关窗口会卡死 —— `close()` 里的 `wait()` 一直在等 demux 线程。

**根因**：`av_read_frame()` 在网络流上可能长时间阻塞（等数据 / 等超时），这个时候 demux 线程其实
已经收到"退出"标志了，却还卡在阻塞的 I/O 里出不来。

**解决**：给 `AVFormatContext` 注册**中断回调**（`interrupt_callback.callback/opaque`），
回调里直接返回退出标志 —— 这是 FFmpeg 官方推荐的"随时可中断"做法；同时用 `rtsp_transport=tcp`、
`max_delay` 这些参数控制网络延迟。

我现在写任何可能长时间阻塞的 I/O，都会先想一下"退出的时候它怎么被打断"。

## 18. Linux 移植：GCC 不会沿"包含链"去找相对路径的头文件

**现象**：Windows 上编得好好的工程，Ubuntu 上第一次 `cmake --build` 就停在这行：

```
ui_player.h:19:10: fatal error: ctrlbar.h: No such file or directory
```

**排查**：`ctrlbar.h` 明明就在旁边，`ui_player.h` 也是 uic 生成的，路径看着都对。

**根因**：`ui_player.h` 生成在**构建目录**里，而 `ctrlbar.h` 在**源码目录**里。MSVC 会沿着
"谁 include 了我"这条链继续往上层找相对路径，GCC 不会 —— 它只认 `-I` 列表和当前文件所在目录。

**解决**：把源码目录显式加进 include 路径：

```cmake
target_include_directories(QtPlayer PRIVATE ${CMAKE_CURRENT_SOURCE_DIR})
```

## 19. Linux 移植：LP64 下 `int64_t` 不是 `long long`

**现象**：

```
error: no declaration matches 'void DemuxThread::videoCallSeek(int64_t)'
```

**根因**：头文件里的槽声明写的是 `long long`，实现里写的是 `int64_t`。Windows（LLP64）上两者是同一个类型，
Linux（LP64）上 `int64_t` 是 `long` —— 于是 moc 生成的声明和我的实现对不上，签名不同就是两个函数。

**解决**：实现和声明统一成 `long long`（跟 Qt 信号槽签名保持一致）。

**认知点**：跨平台时**别把 `int64_t` 和 `long long` 当同义词**；`long`、`size_t` 的宽度也是同理。
信号槽的签名更要按 Qt 的类型写，因为它会被 moc 展开成字符串做匹配。

## 20. Linux 移植：文件系统区分大小写

**现象**：`#include "VideoWidget.h"` 在 Windows 上能过，Linux 上直接找不到文件（实际文件名是 `videowidget.h`）。

**根因**：Windows 的文件系统不区分大小写，把这类错误**掩盖**了很久；ext4 区分，一次就暴露。

**解决**：统一成实际文件名，顺手把项目里的头文件名规范了一遍。

**认知点**：改文件名/重构之后要重新完整 build 一次，别指望增量编译替你发现这种问题。

## 21. Linux 移植：Wayland 下客户端不能自己移动/缩放顶层窗口

**现象**：Linux 上标题栏拖不动、边缘缩放完全没反应。

**根因**：Wayland 的 xdg-shell 里，顶层窗口的位置和大小由**合成器**决定，客户端的 `move()` / `setGeometry()`
会被忽略（或者回弹）；X11 时代那套"自己算坐标自己 setGeometry"不成立了。

**解决**：在**鼠标按下事件的处理里同步调用**：

```cpp
window()->windowHandle()->startSystemMove();          // 标题栏拖动
windowHandle()->startSystemResize(edges);             // 边缘/四角缩放
```

Qt 会分别走 Wayland 的 `xdg_toplevel.move/resize`、X11 的 `_NET_WM_MOVERESIZE`、Windows 的
`WM_SYSCOMMAND(SC_DRAGMOVE / SC_SIZE...)`。返回 false 时再回退到自绘实现。

**这里我踩了第二个坑**：原生移动/缩放是**模态循环**，期间 Qt 不跑事件循环 —— 所有"投递"的事件
（解码、渲染、重绘）都被压到松手之后才处理，于是**边拖窗口边播会明显卡顿**（v2.1 是自绘，走正常事件循环，所以不卡）。
最后我改成：**只有 Wayland 用系统接管**（那里确实没有别的办法），X11 / Windows 一律保留自绘。

**认知点**：跨平台不是"哪个 API 能用就用哪个"，而是"**这个平台上有没有别的选择**"。

## 22. Linux 移植：显示控件不对，最后发现是"编译用的 Qt 不是要跑的那个"

**现象**：Ubuntu 上画面区域不对 —— 显示控件和 topMenu / ctrlbar 之间总留一段距离，画面像是被截掉一条；
同一份代码在 Windows 上完全正常。

**排查**：我怀疑过一圈，并且逐条验证掉了：
- 布局的高度公式（`-12` 那个常数）→ 对当前 `player.ui` 跑 uic，生成的是
  `setContentsMargins(6, 6, 6, 6)`，是 `.ui` **显式**写的，两平台必然一样；
- 两个弹簧（`aboveSpacer` / `belowSpacer`）在 Linux 上没生效 → 把窗口拉到接近 16:9 时缝会自己消失，
  而且上下留白的比例（458 / 382 ≈ 344 / 326）正好等于两个弹簧的 `sizeHint` 比，说明它们**是**生效的；
- 构造函数里栏高拿到的是布局前的默认值 → 打印出来是 `topMenu=50 ctrlbar=56`（`.ui` 给两个栏都设了
  min == max，`setMinimumSize()` 会立刻把几何钳到最小值），所以第一次 `resizeEvent` 拿到的就是真值；
- `QDockWidget` 的 title bar 算进了宽度 → 它默认 `hide()`，隐藏控件不参与布局，而且 title bar 是横的，
  只会撑高 dock 自己。

**根因**：**我编译时用的 Qt 不是我以为的那一个。**之前是

```bash
cmake .. -DCMAKE_PREFIX_PATH=/usr/lib/qt6                      # 系统自带的那份 Qt
```

现在改成自己装的：

```bash
cmake -DCMAKE_PREFIX_PATH=/home/lcy/Qt/6.11.2/gcc_64/lib/cmake/Qt6 ..
```

系统 Qt 和自装 Qt 的版本、平台插件、渲染后端都不一样，混着用就会出现"代码看着没问题、行为就是不对"的现象，
而且报错不会指向真正的方向。

**解决**：构建时显式指向要用的那一份 Qt；这类问题的第一步是**确认版本**，不是读代码。可以互相印证：

```bash
ldd ./QtPlayer | grep -i qt6          # 运行时到底链的是哪份库
cmake -LA -N . | grep Qt6_DIR         # 配置时找到的是哪份 Qt
qmake -query QT_VERSION               # 那份 Qt 的版本
```

**认知点**：**先确认"我到底在跑哪个 Qt"，再怀疑自己的代码。**我把这一圈"看着都合理的怀疑"全部排除掉，
才发现问题根本不在代码里。

## 23. Linux 移植：打开文件后崩溃在 QtMultimedia 音频端点（决定先放着）

**现象**：换成正确的 Qt 之后，Linux 上重新打开文件依旧会崩溃（Qt Creator 弹 `SIGSEGV`）。

**栈（这条栈非常关键）**：

```
1  QPlatformAudioEndpointBase::updateStreamIdle(bool, QPlatformAudioEndpointBase::StreamType)
2  ??
3  QObject::event(QEvent *)
4  QApplicationPrivate::notify_helper(QObject *, QEvent *)
5  QCoreApplication::notifyInternal2(QObject *, QEvent *)
6  QCoreApplicationPrivate::sendPostedEvents(QObject *, int, QThreadData *)
...
11 QEventDispatcherGlib::processEvents(...)
12 QEventLoop::exec(...)
13 QCoreApplication::exec()
14 main                                            main.cpp:10
```

**目前的判断**：崩溃点**根本不在视频/GL 那条路上**，而是在 **QtMultimedia 的音频端点**里，
并且是**通过投递事件在 GUI 线程里执行时**崩的（`sendPostedEvents` → `QObject::event`）。
也就是很可能是音频 sink 的生命周期和我们 seek / 暂停的调用时序撞上了。

**决定：先不修。** 等把 `core` 抽出来、音频输出换成我们自己的 `platform` 层（`IAudioSink`）之后再看 ——
那时候这条路径上的 Qt 代码会少一大截，问题要么自己消失，要么变得能定位。

**认知点**：**崩溃栈告诉你的第一件事是"别在错的地方找"。** 我一开始一直在视频/GL 里翻，实际一行都不在那儿。

## 附. 单测与 CI（工程化）

这一块不是"修 bug"，但它是**敢重构的前提**：逐帧那块是全项目最绕的地方（未来环 + 历史 deque + 游标 + 回填坐标），
我在那里踩过自死锁、淘汰活锁、时间戳坐标不统一。没有测试，我根本不敢动后面的 `core` 抽离。

**测试程序（`tests/test_framequeue.cpp`）**
- 它就是一个带 `main()` 的普通可执行文件，不是测试框架：造带真实 buffer 的假 `AVFrame` → 按状态机一步步走 →
  每处 `CHECK(...)` 断言；跑完打印 `ALL TESTS PASSED`，**没有失败返回 0、有失败返回非 0**
  （后面这一点是它能被自动化使用的前提）。
- 覆盖 6 组：前进 / 后退、历史耗尽触发回填、回填后接续、到文件开头、回填失败不重复请求、历史容量与淘汰、清空。
- 只依赖 `Qt6::Core` + FFmpeg，**不创建窗口、不建 `QApplication`**，所以能在无桌面环境直接跑。

**测试运行器（`ctest`）**
- `ctest` 是 CMake 自带的，也不是测试框架：用 `add_test(NAME framequeue COMMAND test_framequeue)` 把测试注册进构建系统，
  之后一条命令跑全部并汇总结果。
- 最值钱的地方：**有任何一个测试失败，它自己就返回非零退出码** —— 所以 CI 里一行就够，不用自己写脚本汇总。
- 常用参数：`--test-dir build`、`--output-on-failure`（只在失败时打印该测试的输出）、`-R 名字`（只跑匹配的）、
  `--repeat until-fail:50`（重复跑，专门抓偶发）、`-j4`（并行）。
- `set_tests_properties(... ENVIRONMENT "QT_QPA_PLATFORM=offscreen")` 是按**测试**注入环境变量，是防御性的：
  即使以后有人往测试里加了 QtGui 相关的东西，无桌面环境也不会因为"找不到平台插件"而失败。

**CI（GitHub Actions）**
- 一句话：每次 push 都有一台**全新的干净机器**替我做「拉代码 → 装依赖 → 从零构建 → 跑测试」，结果直接标在那次提交上。
- `runs-on: ubuntu-24.04` 那台机器**本身就是无桌面的**（没有桌面会话、没有 GPU，GL 只能软件渲染）——
  所以我不用自己维护一台无桌面 VM，也不用再手工在 VM 里 apt + cmake + ctest 一遍。
- 配置就是仓库里的 `.github/workflows/ci.yml`：`on: push / pull_request / workflow_dispatch`
  （最后一个可以在网页上手动点 Run workflow），job 里是一串 step：checkout → apt 装依赖 → cmake 配置 → 构建 → ctest。
- **它能保证什么**：干净机器上从零构建 + 单测通过。这次移植我踩的三个编译错误——`ctrlbar.h` 找不到、
  `int64_t` 签名不匹配、`VideoWidget.h` 大小写——**CI 在第一次 push 就会全报红**。
- **它不能保证什么**：GUI 画面对不对、拖动跟不跟手、音频响不响、性能好不好。那些只能我在有桌面的机器上看。
  分工是：**有桌面的机器管"功能与观感"，CI 管"构建与回归"。**

**什么时候才真的需要自己那台无桌面 VM**：测性能（CI runner 的型号和核数不固定、有噪声，测出来的数没意义）、
长时间稳定性 / 网络流测试（RTSP 挂两小时那种）、以及没有显示器但要跑 GUI（`xvfb-run` + llvmpipe 软件 GL，
只能验证"不崩"，性能无参考价值）。这些都不在现在的计划里。

**一个和 CI 相关的坑**：ci.yml 里如果直接 `apt install qt6-base-dev`，用的就是**系统 Qt**（24.04 上大概是 6.4~6.6），
而我本机是自装的 6.11.2 —— 这正是第 22 条那个坑的翻版。要么在 CI 里用 `jurplel/install-qt-action` 装一份固定版本
（跟本机对齐），要么就得接受"CI 绿、但行为和我本机不一样"。FFmpeg 那一侧继续用 `pkg-config` 就行。

**常用命令**

```bash
./build/test_framequeue                                        # 直接跑，看逐组进度
ctest --test-dir build --output-on-failure                     # CI 用的就是这条（MSVC 多配置要加 -C Release）
```

## 附. 未来的 core（零 Qt 内核）

这是 P2 的主体，先把边界和判据写在这里，做的时候直接往下填。

**目标**：demux / decode / 帧队列 / 音画同步这些**逻辑**完全不依赖 Qt，只用 C++ 标准库 + FFmpeg；
线程、窗口、GL、音频设备这些**平台相关**的东西收进 `platform` 层，对外只暴露 `api` 层的稳定接口。

**判据（可以客观检查，不靠感觉）**：`core/` 目录下 grep 不到任何 `#include <Q...>`，也不链接 Qt 的库。

**现在的耦合现状（起步点）**：

| 文件 | 依赖的 Qt |
| --- | --- |
| `audiothread.h` | 零 Qt 头（已经是"纯"的） |
| `framequeue.h` | 只用了 `QObject`（其实并不需要） |
| `demuxthread.h` | `QThread` + `QSet` |
| `decodethread.h` / `videorenderthread.h` | `QThread`（+ `QElapsedTimer`） |
| `videodecodethread.h` / `audioplayer.h` | `QObject` |
| `perfclock.h` | `QtGlobal` / `QDebug`（只是打日志） |

**要替换的点**：
- 线程壳：`QThread` → `std::thread` + 自己的停止/唤醒原语（`std::condition_variable`）
- 容器：`QSet` → `std::unordered_set`
- 时钟与日志：`QElapsedTimer` → `std::chrono`；`qDebug` → 自己的日志回调
- 跨线程通知：从"依赖 AutoConnection 的隐式判断"改成**显式队列投递**（问题 16 那条的落地）
- 时间基准：统一到一个 `steady_clock` 纳秒源（`perfclock.h` 已经是这个方向）

**推进顺序**：先拿已经有单测的 `framequeue` / seek 状态机开刀 → 再换 `demuxthread` 的线程壳 →
最后才是渲染和音频的 `platform` 后端。

## 附. 移植 Android

寒假集中做（P3）。先把要过的关记下来，免得到时候从零查。

**目标**：NDK 交叉编译 `core`，写 Java/Kotlin 壳 + JNI，画面走 `Surface` / EGL，音频走 `Oboe`，
解码接 `MediaCodec`；先让最简单的 video + audio 播起来，再谈其他。

**预判的关卡**：
- **构建**：`core` 必须真的零 Qt，否则 NDK 里编不过；用 `android.toolchain.cmake`，只编 `core` + JNI 胶水
- **渲染**：`QOpenGLWidget` 在 Android 上不存在，要 `ANativeWindow` + EGL；现在这套三平面 `GL_RED`
  上传可以直接复用，但外部纹理（`SurfaceTexture` / `GL_OES_EGL_image_external`）要另开一条路
- **音频**：`QAudioSink` → `Oboe`（AAudio / OpenSL ES），还要处理采样率切换和低延迟模式
- **硬解**：`MediaCodec` 输出到 `Surface`，跟现在软解的 YUV 上传是两条路，需要在 `platform` 层做后端切换
- **生命周期**：Android 的 pause / resume / 旋转要重新映射成"暂停 / 继续 / 重建 Surface"
- **验证顺序**：先用 `adb shell` + 日志确认时序对不对，再谈真机性能
